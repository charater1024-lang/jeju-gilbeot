# 제주 길벗 v6 상담형 챗봇 명세

## 구현 방식

LLM·생성형 API·외부 서버를 사용하지 않는다. 고객 서비스 챗봇처럼 준비된 메뉴를 선택하거나 짧은 질문을 입력한다. 규칙이 의도와 지역·테마를 정하고, 기존 관광/음식 TF-IDF 검색 모델로 후보를 찾는다. 장소 안내는 실제 원자료 필드로 미리 렌더링한 문장을 읽는다. 질문을 자유롭게 이해하거나 없는 사실을 생성하는 방식은 아니다.

| 준비 자료 | 개수 | 의미 |
|---|---:|---|
| 직접 작성한 서비스 FAQ | 26 | 이용 방법·자료 범위·위치/오프라인 안내 등의 고정 시나리오 |
| 관광·자연 장소 안내 | 1,148 | 기존 대표 10개와 OSM 관광·자연 1,138개 출처 기록 |
| 허브 여행장소 명부 안내 | 5,381 | 관광 분류 미확인 명부이며 관광지 확정 통계와 분리 |
| 음식 업소 안내 | 27,056 | 허브 인허가 20,954개와 독립 OSM 업소 6,102개 |
| 사전 렌더링 장소 안내 합계 | **33,585** | 출처별 기록마다 안내문 1개. 고유 장소 수나 사람이 작성한 FAQ 33,585개라는 의미가 아님 |

사전 안내문은 이름·관측 분류·실제 소개문(있는 경우)·주소(있는 경우)·좌표·기록/수집 시점·출처를 조합한다. 영업시간·전화·이용료·휠체어·주차는 원자료에 그 태그가 존재할 때만 포함한다. 없는 값은 미확인으로 남긴다. 후속 필드 질문은 같은 원자료에서 고정된 답변 틀을 선택한다. 매번 외부 모델로 새 문장을 생성하지 않는다.

추천 표시에서는 정규화된 이름이 같고 관측 좌표가 500m 이내인 출처 기록만 묶어 대표 관광 정보를 우선한다. 좌표가 없거나 같은 이름이 다른 지역에 있는 경우 임의로 하나의 장소라고 합치지 않는다. 원본 안내문 33,585개는 그대로 보존한다. 전수 고유 장소 중복 제거로 표현하지 않는다.

## 기능과 대화 흐름

- ‘관광지 추천’ → ‘북부 해변 추천해줘’ → 카드/번호 → ‘두 번째 장소 알려줘’ → ‘주소 알려줘’ / ‘영업시간은?’
- ‘다른 곳 추천’은 같은 테마의 다음 후보를, ‘서부로’는 지역을 바꾼 같은 테마의 후보를 보여준다.
- ‘먹거리 추천’ → ‘고기국수 먹고 싶어’ → 업소 기록 → 번호와 상세 질문.
- ‘함덕해수욕장 주소’, ‘성산일출봉 정보’처럼 이름을 직접 입력한다. 같은 이름의 여러 기록은 주소·출처 후보를 보여 주고 번호 선택을 요청한다.
- ‘데이터 출처’, ‘여행 일정 사용법’, ‘LLM을 쓰나요?’ 등 준비된 이용 안내를 제공한다.
- 장소 카드의 상세·지도·여행 담기는 기존 화면 기능에 연결한다. 챗봇 답변만으로 일정을 자동 변경하지 않는다.

지역은 북부·동부·서부·남부·제주 전체 규칙을 사용한다. 관광 테마는 해변/바다·박물관·숲·오름·산책/공원·전망·정원·역사·동굴을 지원한다. 가족/아이 관련 표현은 공원 후보 검색으로만 연결하며 안전시설을 확인한 가족 적합도 평가로 표시하지 않는다. 비 오는 날 표현은 박물관 검색으로 연결할 수 있지만 모든 공간의 실내 여부와 우천 운영을 보장하지 않는다.

## 오답을 줄이는 경계

- ‘지금·현재 영업·오늘 영업·날씨·실시간 교통·잔여 주차’는 명칭이 포함돼도 현재 확인 불가를 먼저 안내한다. 일반 ‘영업시간’은 원자료 표기만 제공한다.
- ‘해변 말고 박물관’, ‘북부 관광지는 싫어’ 등의 제외/부정 조건은 아직 처리하지 않는다고 알리고 원하는 긍정 조건을 다시 요청한다. 기존 검색 조건을 임의로 바꾸지 않는다.
- 무관한 질문과 fallback은 직전 지역·테마·검색 페이지를 오염시키지 않는다.
- 이전 장소를 상속하는 필드 질문은 ‘주소 알려줘’, ‘그곳 영업시간은?’ 등 짧고 명확한 표현으로 제한한다. ‘서울역 주소 알려줘’, 미등록 장소명은 이전에 고른 함덕 주소로 답하지 않는다.
- ‘함덕 근처 카페 주소’ 같은 관계 질문은 해변 주소로 바꾸지 않고 지도 기준 장소 기능을 안내한다. 짧은 별칭은 질문의 앞뒤 표현도 확인하므로 미등록 ‘함덕우리집’을 해변으로 인식하지 않는다.
- 메뉴·서비스 데이터 FAQ를 장소의 출처 질문과 구분한다. ‘데이터 출처’는 서비스 전체 자료를, ‘출처 알려줘’는 선택 장소의 출처를 안내한다.
- 추천 결과는 문자 관련도·분류 후보이며 맛·인기도·개인 만족도 정답을 학습한 평가가 아니다. 질문을 해석하지 못하면 메뉴와 짧은 질문 예를 제공한다.

실시간 확인·예약·결제·사람 상담원 연결·일반 전문 상담은 지원하지 않는다. 현재 운영·입장료·개방·실제 메뉴·탐방 입구·차량 진입·날씨를 원자료만으로 확정하지 않는다.

## API와 상태

서버 통합 함수:

```python
chat_reply(root, {"message": "북부 해변 추천", "state": {}})
chat_status(root)
```

요청 message는 300자 이내 문자열이다. state는 `region`, `topic`, `last_place_id`, `choice_ids`, `last_query`, `offset`만 허용한다. 유효한 공개 DB ID·허용 지역/주제·검색어 길이·페이지 범위를 다시 확인하고 임의의 GPS/추가 필드를 제거한다. 서버 세션을 생성하지 않으며 요청마다 클라이언트가 상태를 전달한다. 대화·질문·기기 좌표를 파일/모델/브라우저 저장소에 기록하지 않는다.

응답은 `reply`, `cards`, `quick_replies`, `state`, `intent`, `answer_source`, `offline:true`, `llm_used:false`를 제공한다. `answer_source`는 FAQ, 준비한 장소 문장, 기존 모델 검색, 명확화 질문을 구분한다. 카드에는 출처·기록 시점·미확인 조건을 포함한다. 상세 필드 중 원문 태그 값은 현재 상태가 아니라 원자료 표기임을 명시한다.

현재 기기의 위치를 챗봇에서 요청하지 않는다. 가까운 장소 질문에는 기존 지도 화면의 기준 장소/위치 권한 선택을 안내한다. ‘새 대화’는 챗봇만, 사이트의 ‘새 여행 시작’은 기존 여행 상태와 대화를 함께 초기화한다.

## 파일과 확장

- `config/chatbot_faq.json`: 직접 작성한 26개 시나리오, 매칭 표현, 버튼과 답변. 안내를 검토한 뒤 추가/수정한다.
- `jeju_agent/chatbot.py`: 의도·지역·테마·후속 규칙, 기존 모델 검색, 자료 기반 답변.
- `scripts/build_chatbot.py`: 기존 관광/음식 색인에서 사전 안내문 재생성. 새 데이터 수집이나 ML 재학습을 자동 수행하지 않는다.
- `data_reference/chatbot.sqlite`: 읽기 전용 답변 DB. 이름/분류/공개 장소 ID와 완성형 안내문을 저장한다.
- `data_reference/chatbot_profile.json`: 자료 수·SHA·생성 시각 범위·방법·한계. 기존 자료의 라이선스·출처 구분을 유지한다.

새 안내문을 늘릴 때는 데이터의 필드를 더 확보하거나 검토한 FAQ를 추가한다. 동일 문장을 의미 없이 반복해 답변 개수를 부풀리지 않는다. 서비스 만족도 정답이 있는 평가 자료를 추가하기 전에는 대화 이해율·추천 정확도를 주장하지 않는다.

## 검증과 현재 개발 PC 측정

`python -m unittest discover -s tests -p test_chatbot.py -v`의 27개 검증을 통과했다. 명칭·번호·후속 지역·반복 음식 검색·출처 우선순위·명칭 모호성·현재 미확인·부정 조건·무관 질문·미등록 새 장소·짧은 필드 상속·근처 관계와 복합 별칭·입력 오염·DB/모델 불변·외부 네트워크 금지를 확인했다. 결과는 `chatbot_tests_v6.txt`에 있다.

최종 답변 DB는 65,855,488바이트, 생성은 현재 개발 PC에서 약 1.094초였다. 네트워크 연결을 차단한 독립 측정에서 인사 약 2.2ms, 북부 해변 검색 약 126ms, 음식 첫 검색 약 640ms, 장소 주소 약 72ms였다. 측정은 `챗봇벤치마크_v6.json`에 보존했다. 센터 i7-8700 실장비 측정이나 지연 보장 수치는 아니다. 현재 공개 자료를 선택하는 CPU 기능으로 별도 GPU·API 키·유료 모델을 요구하지 않는다.
