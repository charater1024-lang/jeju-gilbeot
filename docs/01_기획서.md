# 제주 길벗 머신러닝 여행 추천 에이전트

제주 AI·빅데이터 활용 AI Agent 개발 챌린지 제안서

2026년 10월 26일 기준 설계

## 제안의 핵심

제주데이터허브의 장소·카드·버스 자료와 제주빅데이터센터의 소비·이동 분석 자료를 활용해, 여행자가 예산과 시간 안에서 방문할 지역과 음식점 후보를 고르고 여행 순서를 만드는 시스템을 개발한다. 머신러닝이 지역·업종 수요를 예측하고, 통합 에이전트가 데이터 검사와 추천·교통·경로 도구를 연결한다.

비전문가도 데이터의 관측 기간과 예측 근거를 살펴보고 조건을 바꿔 다시 분석할 수 있게 한다. 지역별 수요 분석을 여행 일정이라는 이해하기 쉬운 결과로 전달하는 것이 목표다.

## 구현 상태와 목표

현재는 기획, 표준 데이터 계약, 두 종류의 ML 학습 코드, 6단계 실행 기록, 로컬 추천 화면을 구현한 상태다. 동봉한 장소와 방문량은 합성 자료다. 실제 데이터 수집·학습·교통 검증을 완료한 최종 제출물은 아니다.

실제 구현의 우선순위는 지역·업종 수요 예측과 음식점 후보 연결이다. 개별 맛집 인기도와 관측된 인기 동선은 해당 점포 레이블과 집계 OD가 확보된 경우에만 제공한다.

## 기대하는 사용자 가치

- 여행자: 취향과 예산·이동 여건을 함께 고려한 하루 일정
- 도민과 비전문가: 제주 데이터를 직접 분석하고 근거를 확인하는 쉬운 인터페이스
- 센터: 출처와 실행 이력이 남는 재현 가능한 데이터 활용 사례

# 해결할 문제와 사용자 경험

## 문제 정의

여행 계획은 장소 검색, 음식점 선택, 이동 수단 검토, 영업시간과 복귀시간 확인을 함께 요구한다. 인기 장소만 이어 붙이면 이동이 과도해지거나 식사·귀환 조건을 놓칠 수 있다. 지역 소비가 많다는 통계와 개별 식당이 좋다는 평가는 서로 다른 정보다.

이 시스템은 지역 수요의 학습 결과와 사용자의 조건을 결합하고, 추천이 무엇을 근거로 만들어졌는지 함께 보여준다. 확인하지 못한 가격·영업시간·교통 정보를 확정 사실로 말하지 않는다.

## 이용 흐름

사용자는 날짜, 출발지와 복귀지, 시작·마감 시각, 예산, 이동 수단, 자연·음식·문화·휴식 선호를 입력한다. 시스템은 데이터 이용 가능성을 검사하고 수요를 예측한 뒤, 후보를 고르고 이동·체류·복귀 조건을 검증한다.

결과에는 방문 순서, 도착과 체류 시각, 예상 지출, 복귀시각, 추천 이유, 출처와 관측 기준일을 제시한다. 사용자가 예산이나 혼잡 회피를 바꾸면 같은 근거 체계에서 다시 계산한다.

## 핵심 기능

- 지역 수요 분석: 어느 지역·업종의 이용 수요가 높은지 예측
- 음식점 후보 추천: 영업 중 장소와 취향·위치·검증된 보완정보 결합
- 경로 구성: 이동시간·예산·영업·복귀 제약을 만족하는 방문 순서
- 분석 근거 확인: 관측·예측·가정을 구분하고 데이터 부족을 안내

현재 시제품은 1인 하루 여행과 구조화 입력을 지원한다. 다일 일정·예약·실시간 대화는 확장 범위다.

## 확인 수준

공공데이터포털에서 카드 월별 집계와 버스 노선 설명을 직접 확인했다. 일부 센터·음식점 후보는 교육부 연계 메타데이터로 확인했다. 허브 원문은 조사 환경의 접속 제한 때문에 원본 CSV를 취득하지 못했다. 실제 열·기간·코드북·현재 이용조건은 확보 후 확정한다.

공개 카드 자료는 지역·업종 등의 집계이며 개별 점포 방문 레이블이 아니다. 음식점 목록은 상호·주소·영업상태의 기준정보다. 확인된 목록에서 맛·평점·가격·영업시간·방문량을 가정하지 않는다.

원문 링크와 A/B/C 검증 수준은 별도 데이터 조사서에 남겼다. 이 목록은 취득 완료 목록이 아니다.

# 수집과 정제 및 데이터 계약

## 수집부터 학습까지

승인된 CSV 또는 API 기술문서를 확보하고 원본 파일·관측 기간·취득일·이용조건·해시를 기록한다. 실제 API 주소와 인증 방식은 기술문서 확인 후 연결한다. 현재 코드에는 추측한 엔드포인트를 넣지 않았다.

장소는 인허가 식별자와 주소로 지점을 구분하고 폐업·중복을 분리한다. 음식점 통합 목록의 좌표 제외 설명을 고려해 주소 지오코딩과 제주 범위 검수를 수행한다. 영업·가격·체류시간은 별도 근거와 가정 여부를 보관한다.

지역 소비는 동일한 연도의 지역코드·업종코드·월로 결합한다. 이용자 중복과 카드 표본 정의가 다른 통계를 임의 합산하지 않는다. 결측·비공개 기호를 0으로 바꾸지 않는다.

## 입력 계약

- 장소 기준정보: 장소키, 지역, 업종, 주소 또는 좌표, 영업상태, 출처
- 지역 수요: 월, 지역, 업종, 값, 건수·이용자·금액 구분, 출처
- 장소 수요 확장: 일자, 장소키, 실제 관측 방문량, 출처
- 교통 확장: 노선·정류소키, 경유 순서, 운행일, 시간표, 요금과 관측일

시제품은 CSV와 JSON을 사용한다. 운영형은 원본, 정제, 특징, 모델, 추천과 근거를 분리하고 SQLite 등 로컬 저장소에서 시작한다.

## 출처와 권한

공개 페이지의 이용조건과 센터 분석 자료의 반출조건을 구분한다. 원자료·집계 결과·학습모델·대회 ZIP에 대한 허용범위를 각각 기록한다. 두 플랫폼의 같은 원본은 한 데이터 계보로 관리한다.

# 머신러닝을 사용하는 추천 방식

## 1차 모델은 지역과 업종의 수요 예측

월별 카드 이용 건수 등 확인된 관측 단위에 맞춰 다음 기간의 지역·업종 수요를 학습한다. 초기 모델은 log1p 목표의 Ridge 회귀이며 지역·업종 그룹, 계절성과 추세를 입력으로 쓴다. 전월·동월 평균 등 기준모델과 비교한다.

이용 건수와 이용자 수, 금액은 다른 목표이므로 별도 모델로 다룬다. 최소 24개월 이상 이력을 우선 확보하고, 짧은 이력에서 계절성 정확도를 주장하지 않는다. 후속 비교 모델은 Poisson/Tweedie와 트리 회귀다.

## 장소 추천과 경로 탐색

지역 수요는 방문 지역 선택의 맥락 점수다. 개별 음식점의 방문량으로 바꾸지 않는다. 지역 안에서는 취향·업종·위치·검증된 영업 및 가격 정보로 후보를 만든다. 개별 점포 관측이 확보되면 별도의 장소 수요 모델을 학습한다.

현재 장소 시제품은 합성 일방문량을 학습한다. 예측 수요와 태그 일치를 명시적 가중치로 결합한 뒤 빔 검색으로 방문 순서를 고른다. 취향 점수의 규칙과 경로 알고리즘은 학습된 개인화 모델과 구분한다.

## 모델 역할의 경계

수요 예측은 맛·위생·서비스 품질 평가가 아니다. 혼잡 회피는 과거 수요가 낮은 후보를 선호하는 설정이며 실제 대기시간 예측이 아니다. 추천 과정에서 LLM을 사용할 경우에도 수치는 ML 도구가 반환한 값만 사용한다.

현재 지역 모델과 장소 모델은 각각 학습·예측할 수 있다. 실제 지역 예측을 UI의 음식점 후보와 결합하는 운영형 계층은 후속 구현 항목이다.

# 검증과 성능 보고 계획

## 시간 순서로 검증

현재 모델은 앞 80% 기간으로 학습하고 마지막 20%로 검증한다. 같은 날짜나 월이 양쪽에 섞이지 않는다. 평균과 범주 등 전처리 정보는 학습 구간에서만 계산한다. 검증 후 배포 모델은 전체 이력으로 다시 학습한다.

실제 개발에서는 마지막 기간을 독립 테스트로 보존하고 이전 구간에서 여러 번의 시점 이동 검증을 수행한다. 자료 공개 지연을 적용해 예측 시점에 이용 가능한 특징만 사용한다. 미래 실제 날씨나 아직 공개되지 않은 현재 월 집계를 사용하지 않는다.

## 평가를 나누어 측정

| 대상 | 지표와 근거 |
|---|---|
| 수요 예측 | MAE·WAPE, 계절 평균과 이전 기간 기준모델 |
| 후보 순위 | 같은 단위의 관측 상위 지역과 비교 |
| 경로 | 시간·예산·영업·복귀 제약 위반률 |
| 근거 | 출처 연결과 관측·예측 단위 일치 여부 |
| 실행 | CPU 처리시간·메모리·재현 성공 여부 |

개인별 선택·방문 정답이 없으면 개인화 정확도를 측정했다고 말하지 않는다. 버스 승객 수만으로 만차나 지연 예측 정확도를 제시하지 않는다.

## 현재 검증의 의미

동봉한 metrics 파일은 합성 자료의 학습·검증 코드가 작동함을 보여준다. 실제 제주 데이터 정확도나 서비스 성능의 증거는 아니다. 실제 테스트 결과가 기준모델보다 낮으면 이를 그대로 보고하고 모델을 선택한다.

추천 조건 검사와 데이터 진위를 구분한다. 파일 형식 검사가 통과해도 관측의 진위나 원 제공기관의 이용 승인이 자동으로 입증되지는 않는다.

# 전문 에이전트와 통합 구조

## 통합 계획의 목표

통합 에이전트는 사용자 요청에 필요한 자료와 도구를 선택하고, 부족한 근거·불가능 조건·실행 실패를 감지해 제한된 범위에서 다시 계획한다. 전문 도구는 재현 가능한 함수로 유지한다.

| 역할 | 주요 책임 |
|---|---|
| 데이터 탐색과 품질 | 출처·기간·단위·이용조건과 결측 검사 |
| 수요 예측 | 학습 모델 추론과 기준시각 반환 |
| 음식점 후보 | 취향·영업·위치·지역 맥락 결합 |
| 교통 검증 | 운행·환승·막차와 구간 근거 검사 |
| 경로 최적화 | 방문·체류·이동·예산·귀환 조합 |
| 독립 검증과 설명 | 제약 검사와 근거 있는 설명 |

통합 계획 → 데이터 검사 → ML 예측 → 후보 생성 → 교통 검사 → 경로 탐색 → 결과 검증의 순서로 실행한다. 실패 원인은 통합 계획으로 돌아가되 최대 2회 재계획한다.

## 현재 구현과 확장

현재 6개 단계는 Python 안에서 실행되고 각 단계의 상태·시간·설명을 trace로 남긴다. 독립 LLM들의 협상·카탈로그 자동 수집·자율 재계획은 현재 기능이 아니다. 통합 계획과 재계획 상태기계는 운영형 개발 범위다.

선택적 LLM은 자연어 요청의 구조화와 설명을 맡는다. 모델명·버전·전송 항목·비용은 도입 시 확정한다. LLM이나 외부 API 없이도 폼과 ML·템플릿 설명으로 센터에서 실행 가능하게 한다.

# 교통과 경로의 실현 가능성

## 인기 지역 연결과 실제 인기 동선

여러 지역의 이용량이 많아도 동일 여행자가 어느 순서로 방문했는지는 알 수 없다. OD가 없을 때 결과는 인기 지역을 연결한 추천 경로다. 집계 OD가 확보되면 지역 간 전이 확률을 추가할 수 있으나 개인의 하루 전체 시퀀스와 동일하게 해석하지 않는다.

## 이동 수단별 구현

자동차·도보 시제품은 좌표 직선거리를 보정해 이동시간을 추정한다. 실제 도로망·보행 제한·산지·실시간 교통을 반영하지 않으므로 도로 길찾기로 표시하지 않는다. 운영형에서는 검증된 이동시간 행렬로 교체한다.

버스 노선 기본정보만으로 정차 순서·시간표·환승·막차를 알 수 없다. 해당 자료가 연결되기 전에는 버스 경로를 만들지 않고 필요한 자료를 안내한다. 버스 수요 통계와 운행 가능성 검증은 별도 기능이다.

## 경로 제약과 실패 처리

각 후보의 도착·체류·폐점, 모든 이동비와 장소비, 마지막 복귀 구간과 마감시각을 검사한다. 현재 비용은 1인 장소비와 가정한 차량 이동비이며 대여·보험·주차 등은 포함하지 않는다.

조건을 만족하는 후보가 없으면 불가능 원인과 사용자가 바꿀 수 있는 항목을 안내한다. 예산이나 이동 수단을 조용히 변경하지 않는다. 현재 빔 검색은 전역 최적을 보장하지 않는다.

운영형은 식사 시간대·필수 장소·휠체어 접근·인원별 비용을 확장한다. 이 정보 역시 확인 가능한 데이터와 사용자 선택을 기준으로 제공한다.

# 화면 구성과 비전문가의 활용

## 여행 조건과 추천 결과

왼쪽에는 날짜·시간·예산·교통·취향을 입력하고 오른쪽에는 방문 순서와 이동시간·비용을 표시한다. 좌표 개략도는 순서를 이해하도록 돕고 실제 도로 경로와 구분한다.

현재 화면은 합성 자료임을 상단에 표시한다. 각 장소에 예측 수요와 취향 점수를 구분해 보여주고 추천 과정의 단계 기록을 펼쳐 볼 수 있다. 두 데이터 플랫폼의 실제 연결 상태도 미확보로 표시한다.

## 분석 화면 확장

운영형에서는 이용 가능한 데이터와 관측 기간을 선택하고, 지역별 수요와 시간대 차이를 살펴보는 분석 탭을 추가한다. 예측값·기준모델·불확실성의 설명과 출처를 연결하고 결과를 CSV로 내보내도록 한다.

도민이나 센터 방문자가 전문 코드를 작성하지 않고 지역 식음료 소비를 비교하고 그 결과를 여행 추천에 활용할 수 있게 한다. 외부 API 실패나 승인 자료 부족도 화면에서 이해할 수 있어야 한다.

## 검증 시나리오

- 자연과 음식 중심의 자동차 여행에서 예산과 귀환 조건 확인
- 도보의 가까운 후보와 짧은 이동 범위 확인
- 혼잡 회피 선택 시 수요 점수와 후보 변화 확인
- 낮은 예산·짧은 시간의 불가능 조건 안내
- 버스 시간표가 없을 때 제한 기능 안내

사용성 검증은 비전문가 3~5명을 대상으로 수행할 계획이다. 아직 실제 사용자 실험 결과나 만족도 수치는 없다.

# 개발 환경과 센터 실행 계획

## 현재 실행 환경

Python 3.10 이상과 표준 라이브러리만으로 ML 학습·추천·로컬 HTTP 화면을 실행한다. 별도의 pip 패키지·GPU·외부 API Key가 필요하지 않다. 서버는 127.0.0.1에서만 실행한다. 외부 지도와 폰트 CDN에 의존하지 않는다.

센터 공고의 최소 PC 사양은 Intel Core i7-8700, GTX 1060, RAM 32GB다. 경량 표 모델을 CPU로 실행하는 구성을 우선한다. 해당 동일 사양에서의 지연시간·메모리는 별도로 측정해야 한다.

## 산출물 구조

- docs: 기획서, 데이터·ML·Agent 설계, 일정과 매뉴얼
- jeju_agent: 수요 학습·추천·집계 모델·검증·로컬 서버
- data와 examples: 합성 장소·방문량, 월별 예시와 입력 요청
- models: 학습한 JSON 모델과 합성 검증 지표
- tests와 prompts: 검증 코드, 향후 LLM 연결 명세

## 외부 의존성 관리

실제 데이터 수집·지오코딩·도로 이동행렬·선택적 LLM은 후속 연결 대상이다. 공급자·호출한도·요금·약관·캐시 허용범위·전송 항목을 도입 전에 기록한다. 현재 이 서비스들이 연결되었다고 표시하지 않는다.

원본 자료가 재배포 불가하면 ZIP에 포함하지 않고 적법한 센터 내부 실행 또는 재취득 절차를 제공한다. API Key는 환경변수로 주입하며 제출물·화면·로그에서 제외한다.

# 개발 일정과 범위 관리

## 마감까지의 구현 순서

| 기간 | 주요 작업 |
|---|---|
| 10월 26~28일 | 데이터 요청과 명세·권한·집계 단위 확인 |
| 10월 29일~11월 2일 | 실제 수집·주소와 코드 정제·품질 보고 |
| 11월 3~6일 | 실제 수요 모델·기준모델·시간 검증 |
| 11월 7~11일 | 지역 점수 결합·이동행렬·추천 화면 |
| 11월 12~15일 | 센터 환경과 비전문가 시연 검증 |
| 11월 16~19일 | 출처·반출·재현·문서·ZIP 검토 |

제출 마감은 2026년 11월 20일 오전 10시 한국시간이다. 전날까지 실행 리허설과 ZIP 확인을 마치는 일정으로 제안한다. 실제 참가 신청이나 제출은 이 패키지 생성에 포함되지 않는다.

## 범위 축소 기준

점포 레이블을 확보하지 못하면 지역 수요와 후보 추천을 완성한다. 버스 운행 그래프가 없으면 버스 수요 분석만 제공하고 길찾기는 제한한다. OD가 없으면 실제 인기 동선이라는 표현을 사용하지 않는다.

두 플랫폼에서 가능한 자료를 최대한 기능에 연결하되 같은 원본의 중복 집계나 검증되지 않은 데이터 목록 수를 성과로 쓰지 않는다. 추가 모델보다 실제 한 종류 이상을 적법하게 학습·재현하는 것이 먼저다.

1인 또는 팀 개발 모두 가능하며 데이터 정제, 모델 평가, 경로 교통, UI, 통합 제출로 역할을 나눌 수 있다. 외부 API 비용은 공급자를 확정한 뒤 별도 산정한다.

# 현재 검증과 후속 완료 조건

## 실행 시제품에서 확인하는 항목

장소별 합성 자료 30개와 일별 관측 5,340행, 월별 지역·업종 합성 예시 144행을 제공한다. 두 모델은 시간 순서 검증과 기준모델 비교를 수행한다. 모델·검증 JSON에 합성 상태와 한계를 기록한다.

단위 검증은 미래정보 누수, 데이터 중복·음수·측정값 혼합, 모델 파일의 차원과 값, 학습 데이터 변경, 예산·폐점·복귀, 버스 기능 제한 등을 검사한다. 실제 실행 결과와 테스트 수는 별도 검증결과 문서에 기록한다.

## 실제 서비스 완료를 위한 남은 작업

- 제주 원본 자료와 코드북을 취득하고 출처·권한·관측기간 검증
- 실제 지역 수요 모델의 독립 테스트와 기준모델 비교
- 음식점 좌표와 검증된 보완정보, 지역 모델과 후보의 결합
- 도로 이동행렬과 버스 운행 그래프 연결 및 경로 검증
- 통합 에이전트의 도구 선택·재계획과 분석 화면 확장
- 센터 환경·비전문가 시연과 재현 가능한 최종 ZIP

현재 패키지를 실제 자료 성능이 검증된 최종 제출물로 제시하지 않는다. 합성 점수로 추천 정확도나 대회 성과를 주장하지 않는다.

## 제출 전 확인

기획서 분량, 실행 코드, 모델과 라이브러리 정보, 외부 의존성, 데이터 출처·이용조건, 오류 대응, 검증 한계를 맞춘다. 센터 소속·제공에 관한 대회 소유권 문구와 제3자 권리를 함께 확인한다. 세부 심사 배점은 이번 조사에서 확인되지 않아 임의로 반영하지 않았다.
