# 제주 길벗 여행 추천 서비스 기획서

현재 구현과 자동 코스 추천 고도화 계획

2026년 10월 31일 | 구현 기준 v13 | 기획 개선판

## 1 사업 개요와 제안 방향

제주 길벗은 제주데이터허브와 제주빅데이터센터 자료를 여행 탐색과 일정 구성에 연결하는 로컬 웹 서비스다. 센터를 방문한 도민과 관광객이 자신의 조건을 입력하고 추천 근거를 확인하도록 돕는다. 이번 개선안은 현재 v13 시제품을 기반으로, 사용자가 요청할 때 현재 위치 또는 직접 고른 출발지에서 자동 코스를 만드는 기능을 우선 개발하는 계획이다.

### 핵심 제안

거리·취향·이용 가능 시간으로 관광지와 식사 후보를 고르고 방문 순서를 구성한다. 장소 연결 근거와 정보 기준일을 함께 보여주며, 실제 방문·선호 데이터가 검증된 뒤에만 인기 경로 특징을 추가한다. 인터넷이 끊겨도 센터 PC의 기본 추천과 위치 참고도는 동작하도록 유지한다.

| 현재 기반 | 확인한 범위 |
| --- | --- |
| 관광 후보 | 허브 명부와 지도를 교차확인한 68개 후보, 대표 사진 카드 6개 |
| 관광 소개 | 공식 관광 자료에 근거한 소개 62개, 미연결 6개 |
| 음식 검색 | TF-IDF를 학습한 출처 기록 27,056개, 고유 업체 수와는 구분 |
| 실행 환경 | 센터 PC의 로컬 브라우저와 내장 Python, 핵심 기능은 LLM과 API 키 없이 실행 |

### 개선 우선순위

- P0  위치를 실제 일정 출발점에 연결하고 관광지 입구와 정보 정확성을 검수한다.
- P1  학습된 검색 관련도와 거리·시간 제약으로 장소 자체를 고르는 자동 코스를 만든다.
- P2  이용권한과 관측 단위가 검증된 이동·선호 자료를 확보한 뒤 경로 선호를 학습한다.
- P3  제주 제공 범위와 최신성이 검증되는 경우에만 실시간 교통을 선택 적용한다.

> 문서 기준  시제품은 v13이다. P0부터 P3까지는 개발 계획이며 완료된 기능이 아니다. 공고의 15페이지 이내 분량과 센터 실행 조건에 맞춰 구성했다. [E1, L1]

## 2 사용자 문제와 서비스 범위

현재 위치에서 갈 만한 장소를 찾는 일과 실제로 방문 가능한 하루 코스를 만드는 일에는 서로 다른 정보가 필요하다. 상호·관광지 이름만으로 식당의 메뉴나 현재 영업을 알 수 없고, 대표 좌표가 산 정상이라면 자동차 도착지로 쓸 수 없다. 제주 길벗은 이런 차이를 사용자가 이해할 수 있는 여행 화면으로 설명한다.

| 이용자 | 해결할 문제 | 제공 가치 |
| --- | --- | --- |
| 관광객 | 낯선 지역에서 관광·식사·복귀 순서 결정 | 출발지와 남은 시간에 맞는 코스와 근거 확인 |
| 도민 | 가까운 새 장소와 짧은 나들이 탐색 | 거리와 선호 테마 중심의 반나절 코스 |
| 센터 방문자 | 데이터 분석 도구 사용의 어려움 | 조건 선택과 상담 버튼으로 데이터 탐색·분석 체험 |
| 센터 운영자 | 자료 갱신과 공용 PC 운영 | 버전·출처·검증 기록과 세션 초기화 절차 |

### 우선 운영 범위

최종 결과물은 센터에 직접 방문한 이용자가 설치된 PC에서 실행하는 방식을 우선한다. 1인 또는 동행 그룹의 제주 본섬 하루 일정, 자동차와 도보 계획을 대상으로 한다. 공용 PC에서는 제주공항·숙소·관광지 등 출발지를 직접 지정하는 흐름을 기본으로 제공한다. 기기 위치가 센터 위치라는 점도 분명하게 안내한다.

### 장기 웹 서비스 확장

관광객과 도민이 개인 기기에서 이용하는 공개 웹 서비스는 다음 단계다. HTTPS 배포, 위치 권한, 동시 이용, API 키 관리, 서버 보관 정책과 운영 비용을 별도 검증한다. 현재의 127.0.0.1 로컬 서버를 외부 서비스로 공개한 상태라고 설명하지 않는다.

### 제출 범위에서의 제한

예약·결제, 배편과 버스 환승 시간표, 실시간 잔여 좌석·주차면, 무검증 맛집 순위는 필수 범위에 넣지 않는다. 도보는 실제 보행 경로와 접근성 확인이 부족하면 거리 기반 계획으로 표시한다. 이동수단이나 장소의 근거가 부족할 때는 지원하지 않는 이유와 대체 선택을 안내한다.

> 목표는 모든 관광정보를 많이 보여주는 것이 아니라, 근거가 있는 후보로 실행 가능한 계획 초안을 제공하고 미확인 항목을 사용자가 알아볼 수 있게 하는 것이다. [E1, L1, L2]

현재 시제품은 실제 데이터 검색과 지도·상담·일정 기능을 갖추고 있다. 아래 표는 코드와 저장된 검증 보고서를 기준으로 한 현황이며 현장 정확도나 센터 최소사양 성능을 측정한 결과표는 아니다.

| 기능 | 상태 | 현재 동작과 남은 범위 |

### 분석과 학습의 실제 역할

관광 68개와 음식 출처 기록 27,056개의 TF-IDF 표현을 실제로 학습해 검색에 사용한다. 센터 카드·승차 분석은 후보 모형보다 검증오차가 낮았던 집단 평균과 요일·시간대 평균을 운영 출력으로 선택했다. 이 분석 결과가 개별 식당 인기나 방문 순서를 직접 학습한 것은 아니다.

> v13 저장 보고서에는 Python 테스트 166개와 UI 13개 파일 및 문법 검사 1개 통과가 기록돼 있다. 기능 검증과 장소 정합성·추천 만족도 평가를 분리하며, 이번 문서 작성 중 앱을 수정하거나 이 검증을 다시 실행한 것은 아니다. [L1, L2, L6]

### 원본과 배포 관리

원본 파일은 취득일·관측 기간·열·제공처·해시와 함께 보존하고 가공 규칙과 모델 버전을 연결한다. 현재 다운로드 명세에 원본 라이선스 확인과 재배포 승인이 미확인으로 남은 항목은 제출·센터 반출 전에 확인한다. 연계 포털의 라이선스 문구만으로 원본 배포 권한을 확정하지 않는다.

> 장소 명부의 마지막 행 수정일은 2025년 9월 18일, 음식 명부는 2025년 9월 2일이다. OSM 수집 시점 2026년 10월 28일은 개별 기록의 최신성을 뜻하지 않는다. 음식 27,056개도 고유 맛집 수나 거리 추천 가능 수가 아닌 출처 기록 합계다. [L3, L4, E2, E3]

## 5 데이터 정확성 확보와 검수 기준

이름·대표 위치가 비슷하다는 이유만으로 실제 방문 가능성을 확정하면 잘못된 코스가 만들어진다. 자료 수집, 장소 연결, 실제 접근, 현재 운영을 각각 검사하고 자동 코스에 넣을 수 있는 범위를 단계별로 정한다.

### 현재 교차확인 기준

관광지는 허브와 지도의 정규화 이름이 정확히 같고 직선거리 250m 이내인 기록 중 분류 검사를 통과한 후보만 제공한다. 식당·숙박·상점·일반시설은 관광 후보에서 제외한다. 표시 이름은 허브를 우선하고 원래 지도명과 양쪽 근거는 보존한다. 이 기준은 현장 정답이나 공식 지정 관광지 인증을 뜻하지 않는다.

| 도입할 검수 단계 | 통과 근거 | 자동 코스 처리 |
| --- | --- | --- |
| 후보 연결 | 이름·위치·분류·중복·출처 검사를 통과 | 검색에 표시하고 대표 좌표의 한계를 안내 |
| 접근 지점 검수 | 공식 안내의 입구·주차장·탐방 시작점과 방문 수단을 확인 | 해당 이동수단 코스 후보로 허용 |
| 운영 조건 검수 | 휴무·예약·시간·통제의 출처와 확인일을 기록 | 확인된 조건을 검사. 시간만 미확인인 경우 경고와 교체 기능 제공 |
| 정체성·접근 미확인 또는 폐쇄 충돌 | 이름 변경·위치·입구 불일치 또는 명시된 폐쇄·통제 | 자동 편입을 보류하고 관리자 재검수 목록에 등록 |

### 우선 검수 대상

관광 후보 68개를 전수 검토하고, 명부와 공식 안내명이 다른 장소 및 산 정상·동굴·섬·출입 통제 사례부터 정리한다. 금능식물원과 금능석물원처럼 실제 자료에 있는 이름 차이는 조용히 합치지 않는다. 2020년 기사 등 오래된 소개는 현재 운영 근거로 사용하지 않는다. 음식점은 상호·지점·전체주소와 좌표의 독립 근거가 확인된 소규모 집합부터 확대한다.

### 이력과 화면 표시

장소별로 source_id, 관측 기준일, 취득일, 확인일, 입구 좌표, 검수자, 충돌 사유와 버전을 관리한다. 임의의 신뢰도 퍼센트를 만들지 않고 '명부·지도 연결', '입구 확인', '운영 미확인'처럼 근거를 설명한다. 운영정보의 재확인 주기는 항목별 변경 빈도와 원천 갱신 주기에 맞춰 정한다.

> 출시 검수 목표는 관광 후보 68개 검토율 100%, 확인된 중대한 장소 오연결 0건이다. 목표값이며 현재 달성한 정확도 수치가 아니다. [L2, L3, L5]

## 6 사용자 경험과 자동 코스 요청 흐름

자동 코스는 사용자가 명시적으로 요청할 때 생성한다. 장소를 직접 담아 일정을 만드는 기존 방식도 유지한다. 위치 제공 없이도 출발지를 고를 수 있고, 위치를 받지 못했을 때 제주공항을 내 위치처럼 사용하지 않는다.

### 제안하는 이용 순서

1. 출발 방식 선택  내 위치 사용 또는 지도·기준 장소로 직접 지정한다. 센터 PC에서는 직접 지정 안내를 먼저 제공한다.
2. 여행 조건 입력  날짜·시작과 복귀 시각·자동차 또는 도보·여행 길이·선호 테마·식사 포함 여부를 고른다.
3. 출발점 확인  위치의 정확도·획득 시각과 실제 일정 출발지, 복귀지를 확인한 뒤 자동 코스 만들기를 누른다.
4. 대안 비교  기본 코스와 이동을 줄인 코스 등 최대 3안을 보고 장소·예상 이동·체류 시간과 추천 근거를 비교한다.
5. 사용자 수정  장소 고정·제외·교체와 식사 변경을 적용하고 시간 제약을 다시 검사한다. 저장과 초기화는 기존 기능을 사용한다.

### 대표 이용 시나리오

관광객은 '현재 위치에서 5시간, 바다와 산책, 흑돼지 관련 식사 후보'를 선택한다. 시스템은 동의한 위치를 출발점에 연결하고, 접근 지점이 검수된 관광지와 음식 후보를 고른다. 음식은 확인된 업종·cuisine·상호 근거를 구분하며 실제 메뉴 제공을 보장하지 않는다. 식사 후보의 영업이 미확인이면 별도 확인 표시와 교체 기능을 제공한다.

### 결과에 반드시 보일 정보

- 출발 기준과 복귀지, 방문 순서, 계획용 체류시간, 추정 이동시간·거리, 복귀 예상 시각
- 장소마다 취향 관련도·거리·사용한 지역 통계 또는 방문 전이 근거와 자료 시점
- 입구·운영·요금의 확인 상태와 코스에서 빠진 장소의 이유
- 이동비 추정과 입장·식사·주차비 미포함 여부, 사용자가 직접 수정할 수 있는 항목

> 화면은 제주 둘러보기, 지도·먹거리, 내 여행, 데이터 안내로 나누고 길벗 상담은 기존 팝업 방식으로 유지한다. 자동 코스의 위치 연결과 후보 자동 선택은 신규 개발 사항이다. [L1, L2]

## 7 거리와 취향 기반 자동 코스 설계

자동 코스의 첫 단계는 학습된 장소 검색 표현을 사용해 후보를 찾고, 검수 조건과 거리·시간 제약으로 후보 집합과 방문 순서를 함께 고르는 방식이다. 실시간 정보와 관측 인기 동선이 없어도 작동하는 기본 모드로 개발한다.

### 후보를 고르는 순서

1. 위치·날짜·선호·남은 시간과 이동수단을 검사한다. 오래되거나 정확도가 낮은 위치는 재확인하고 제주 밖 위치는 직접 출발지를 선택하게 한다.
2. 관광·음식 TF-IDF 검색에서 관련 후보를 구한다. 좌표 없는 음식 기록은 거리 코스에서 제외하고 검색 결과에 따로 남긴다.
3. 중복·배편·미검수 산 정상·명시된 출입 통제·이동수단 부적합 후보를 제거한다. 확인된 운영·예약 조건은 시간 제약으로 사용한다.
4. 거리와 체류시간으로 방문 가능한 수를 정하고, 고정한 장소·식사 시간대·테마 다양성을 반영해 후보와 순서를 탐색한다.
5. 귀환까지 포함한 시간을 재계산하고 서로 지나치게 겹치는 코스를 줄인다. 조건을 만족하지 못하면 일정을 꾸며내지 않고 시간 또는 장소 수 조정을 제안한다.

### 탐색과 점수

초기에는 후보를 최대 30곳 안팎으로 제한하고, 선택 수와 시간 상한을 둔 빔 탐색 또는 휴리스틱 탐색을 사용한다. 관련도·거리 부담·선호 테마·중복 방문 감소를 조합한다. 관련도는 학습된 TF-IDF 값이고 나머지 초기 가중치는 설계 규칙이다. 가중치 조합 전체를 사용자 선호 학습의 결과라고 부르지 않는다.

### 시간과 비용의 의미

현재 자동차 시간은 직선거리 보정과 가정 속도로 추정한다. 고도화 단계에서는 검증 가능한 도로 거리와 입구 연결을 우선 개선하고, 실측 자료가 생기면 이동수단·구역별 오차를 보정한다. 체류시간은 출처가 없을 때 계획용 가정으로 표시한다. 입장·식사·대여비가 없는 상태에서는 총예산 충족을 보장하지 않고 추정 이동비와 별도 비용을 분리한다.

> 첫 기본값 제안은 관광 3~5곳과 선택적 식사 1곳이다. 장소 수·탐색 폭·가중치는 성능 시험과 사용자 평가로 정할 설계값이다. 자동 코스 API와 입력·결과 스키마도 새로 구현한다. [L2, L4]

## 8 사람들이 선호하는 경로의 도입 조건

방문량이 많은 지역, 연속해서 이동한 장소, 만족도가 높은 코스는 서로 다른 지표다. 현재 확보한 지역 소비와 승차 집계로 '사람들이 좋아하는 경로'를 만들었다고 주장하지 않는다. 자료가 나타내는 범위에 맞춰 추천 이름과 설명을 바꾼다.

| 확보할 근거 | 가능한 모델·설명 | 사용 조건 |
| --- | --- | --- |
| 지역별 소비·방문 집계 | 과거 지역 이용 경향을 참고한 코스 | 기간·표본·분모·구역 경계 확인. 개별 점포 선호로 해석하지 않음 |
| 익명 집계 OD | 구역 간 이동 전이 가중치 | 방향·시간대·교통수단·관광객 범위 확인. 한 여행의 전체 순서와 구분 |
| 검증된 POI 연속방문 집계 | 관광지 A 다음 B를 방문한 전이 모형 | 관광지 대응표와 최소 집계수·반출 조건이 확인된 경우 |
| 동의 기반 저장·평가 | 코스 선택·완주·만족도별 선호 순위 모형 | 위치 궤적 없이도 수집 가능한 최소 이벤트부터 설계 |

### 센터에 요청할 자료 명세

출발·도착 구역 또는 관광지 ID, 관측 기간, 시간 구간, 방향별 이동건수, 이용자·이동수단 분류, 집계 기준과 최소 표본수, 공간 경계와 이용조건을 요청한다. 현재 공개 조사에서는 바로 취득할 수 있는 특정 센터 관광 OD 상품을 확인하지 못했으므로 확보 여부를 개발 의존성으로 관리한다.

### 학습과 오해 방지

POI 전이가 확보되면 빈도가 작은 전이를 보정한 전이확률을 거리·취향 점수의 보조 특징으로 실험한다. OD만으로 여러 구간을 이어 하나의 실측 여행 궤적처럼 만들지 않는다. 선호 평가가 확보되면 선택과 만족도를 별도 레이블로 학습하고 노출 위치·선택 편향도 검토한다. 인기 편중을 줄이기 위해 테마·지역 다양성도 비교한다.

> 자료 확보가 지연되면 거리와 취향 기반 자동 코스를 제출 핵심으로 유지한다. 지역 경향 참고, 관측 방문 전이, 사용자 선호 학습은 화면과 모델 설명에서 서로 다른 모드로 표시한다. [E2, E3, L4]

## 9 머신러닝 구성과 평가 계획

단순한 평균이나 거리 기준보다 복잡한 모형을 썼다는 사실보다, 같은 평가 조건에서 무엇이 개선되는지를 확인한다. 학습·검증·테스트를 분리하고 좋은 결과가 없는 모형은 운영에 채택하지 않는다.

| 구성 | 현재 상태 | 개선과 평가 |
| --- | --- | --- |
| 관광·음식 검색 | 68개 관광 후보와 27,056개 음식 기록의 TF-IDF 학습 | 대표 검색어·오탈자·지역·음식어 정답 세트로 HitRate와 NDCG 평가 |
| 소비 경향 | 1048 집단 평균을 검증 결과에 따라 운영 선택 | 지역 자료가 확보되면 공간키를 검수한 뒤 기존 평균과 비교 |
| 승차 시간대 | 512 요일·시간대 평균을 검증 결과에 따라 운영 선택 | 경로·좌석·관광객 혼잡 모델과 구분해 분석 참고로 제공 |
| 코스 후보·순서 | 선택 장소의 제약 탐색만 구현 | 자동 선택을 추가하고 거리 기준·수동 선택 기준과 비교 |
| 방문 전이·선호 | 자료와 운영 모델 없음 | 검증된 집계 전이 또는 동의 기반 평가 확보 후 별도 실험 |

### 추천 품질 평가

먼저 관광·음식 의도별 검색 질문 60개 이상과 장소 관련성 판정 기준을 만든다. 검수자는 출처와 장소 정체성을 확인해 후보별 관련도를 평가한다. 코스는 이동 부담, 테마 충족, 다양성, 방문 가능성, 교체 횟수와 만족도를 각각 측정한다. 검색 점수를 여행 만족도 퍼센트로 바꾸지 않는다.

### 학습 누수와 기준 모형

집계자료는 시간순으로 나누고, 동일 여행이나 유사 구역의 기록이 양쪽에 섞여 평가가 쉬워지는지 점검한다. 전이·선호 자료는 시점과 익명 여행 단위로 분리한다. 단순 거리순, 기존 TF-IDF와 고정 가중치 조합을 기준으로 두고, 조건이 갖춰질 때 경량 순위학습 또는 분류 모형을 비교한다. 데이터 수가 부족하면 보정 평균·전이 모형을 유지한다.

### 산출물

모델 파일과 입력 필드, 자료 계보, 학습 기간, 분할 기준, 기준 모형, 지표와 실패 사례를 함께 저장한다. 현재 저장된 과거 소비 구성비 MAE나 승차 오차를 개인별 여행 추천 정확도 성과로 전용하지 않는다. 센터 CPU 추론을 우선하고 GPU와 대형 언어모델을 필수로 요구하지 않는다.

> 정답 세트·사용자 실험과 추천 품질 점수는 앞으로 구축할 평가다. 현재 확인한 기능 테스트 통과 수와 구분한다. [L4, L6]

## 10 지도 경로와 실시간 교통의 도입 계획

기본 서비스는 인터넷 없이 실행되는 거리 추정과 로컬 OSM 도로 참고 경로를 유지한다. 국가교통정보센터의 교통소통정보는 연결 후보로 검토하되, 인증키와 제주 도로 제공 범위가 확인되기 전에는 제출 필수 기능으로 약속하지 않는다.

| 모드 | 사용 자료와 결과 | 도입 상태 |
| --- | --- | --- |
| 거리 기반 | 좌표 간 보정거리와 가정 속도에 따른 시간·비용 추정 | 현재 구현. 자동 코스 기본 모드로 연결 예정 |
| 로컬 도로 참고 | OSM 도로 연결 탐색, 가까운 도로까지 연결 구간 표시 | 현재 구현. 실제 입구·회전 제한·통제는 별도 |
| 실시간 교통 보조 | 제공되는 구간 속도를 검증해 연결된 도로에만 적용 | 키·실응답·제주 범위·링크 연결 검증 후 선택 구현 |

### 연결 전 확인할 항목

1. 공식 API 이용조건과 인증키·호출량, 센터 외부망 허용 여부와 키 보관 위치를 확인한다.
2. 제주 영역의 실제 응답에서 유효 구간, 방향, 생성시각·갱신 지연과 결측·0속도 처리 규칙을 검사한다.
3. 공식 도로 링크와 OSM 그래프를 방향·길이·기하로 대조하고 연결률을 측정한다. 가까운 평행·반대편 도로에 속도를 붙이지 않는다.
4. 실시간 정보가 적용된 거리 비율과 갱신시각을 결과에 표시한다. TTL과 재시도 주기는 공식 명세와 관측 지연을 확인한 뒤 정한다.
5. 인증·네트워크·제공 범위 문제가 있으면 거리 추정으로 복귀하고 실시간 표시를 해제한다. 오래된 캐시를 실시간으로 안내하지 않는다.

### 개인 위치와 교통 조회

방문자 좌표를 외부 교통 서비스에 보내지 않도록 고정 제주 영역 또는 공용 도로 구역 조회를 우선 검토한다. 결과는 로컬 경로에 결합한다. 모바일 기기의 위치 서비스와 외부 지도 타일 사용은 별도의 권한·네트워크 경로임을 설명한다.

> 공식 후보는 국토교통부 교통소통정보와 국가교통정보센터 OpenAPI다. 이번 조사에서는 키 발급과 실제 응답 검증을 수행하지 않았다. 제주 전역 도로의 실시간 제공을 보장하지 않는다. [E4, E5, L2]

## 11 통합 Agent와 시스템 구성

현재 통합 Agent는 역할별 함수를 로컬에서 순서대로 호출하고 실행 근거를 반환하는 도구 파이프라인이다. 고도화에서도 규칙·머신러닝 검색·제약 탐색을 조합하며, LLM이 외부 사이트를 탐색하거나 코드를 실행하는 자율 에이전트는 필수로 사용하지 않는다.

| 역할 | 입력과 책임 | 판단 범위 |
| --- | --- | --- |
| 통합 조정 | 요청 조건 검사와 도구 실행, 오류·버전 기록 | 허용한 워크플로 안에서만 다음 단계 선택 |
| 데이터 품질 | 명부·지도·소개·입구·운영 상태 검사 | 근거 없는 후보 제외와 재검수 요청 |
| 장소와 음식 | TF-IDF 관련도, 지역·거리·음식 근거 | 검증된 속성 범위에서 후보 선정 |
| 경로 선호 | 이용 가능한 지역 경향·전이·평가 데이터 | 실제 근거가 있을 때만 보조 점수 제공 |
| 이동과 제약 | 출발·복귀·거리·체류·수단·시간 | 후보 선택과 순서 탐색, 조건 위반 거절 |
| 설명과 상담 | 고정 템플릿과 결과 근거·대체 선택 | 관측·모형·가정·미확인 항목 구분 |

### 실행 흐름과 자율성

화면 입력 → 위치·조건 확인 → 자료 사용 가능성 검사 → 후보 검색 → 자동 선택·순서 탐색 → 이동·복귀 재검사 → 근거와 대안 제시 순서로 실행한다. Agent는 허용된 후보를 고르고 조합을 재계산할 수 있지만 데이터 수집 권한 확대, 원본 수정, 모델 배포·학습 실행, 예약·결제는 자동 수행하지 않는다. 자료 갱신과 모델 전환은 운영자가 검증 후 수행한다.

### 개발 구성

Python 로컬 서버, SQLite 검색 색인, 로컬 JSON 모델과 HTML·CSS·JavaScript 화면을 유지한다. 현재 관광·상담·계획·도로 API를 재사용하고, 자동 코스용 API와 장소 검수 메타데이터를 추가한다. 제안 API는 출발 근거, 복귀지, 시간, 수단, 선호, 고정·제외 ID를 받고 대안별 방문 순서·점수 근거·자료 버전·제약 상태를 반환한다.

> 담당 역할은 데이터·검수, 추천·경로, UI·사용성, 배포·평가로 나눈다. 이는 개발 책임의 구분이며 실제 참여 인원이나 자율형 다중 Agent 운영 완료를 의미하지 않는다. [L1, L2, E1]

## 12 센터 운영 환경과 개인정보 설계

센터 최소사양인 Intel Core i7-8700, GTX 1060, RAM 32GB에서 비전문가가 실행할 수 있도록 CPU 중심의 가벼운 검색·추천을 유지한다. 현재 패키지는 Python 3.13.17을 포함하지만 최소사양 센터 PC와 보안정책에서의 현장 검증은 남아 있다.

### 설치와 운영

운영자는 run_center.cmd로 로컬 서버와 브라우저를 시작하고 자료·모델 버전과 상태를 확인한다. 핵심 추론에는 원본 대용량 CSV를 매 요청 로드하지 않고 색인과 모델만 사용한다. 방문 종료 후 새 여행 시작과 탭 종료로 다음 이용자에게 이전 조건이 남지 않도록 한다. 다운로드 일정 파일은 센터 파일 보관 절차에 따라 별도로 관리한다.

| 의존성 | 기본 모드 | 추가 검증 |
| --- | --- | --- |
| LLM과 GPU | 런타임 LLM·API 키 없이 핵심 기능 실행 | 신규 모형도 CPU 추론과 메모리 사용을 우선 측정 |
| 네트워크 | 오프라인 자료와 지도 참고도 사용 | 공식 원문 열기·온라인 지도·교통 API는 외부망 필요 |
| 기기 위치 | 사용자 동의와 위치 획득 성공 시 사용 | 센터 위치·오차·오래된 위치를 확인. 실패 시 직접 출발지 선택 |
| 자료 갱신 | 운영자가 원본·이용조건·가공물 검증 | 이전 버전으로 되돌릴 수 있는 모델·색인 단위 배포 |

### 위치와 사용자 피드백

현재 주변 탐색 위치는 메모리에서 공유하고 영구 저장을 요구하지 않는다. 자동 코스 개발 시에도 위치의 목적·범위를 설명하고 정밀 좌표를 서버 로그나 다운로드 일정에 기본 포함하지 않도록 검사한다. 공개 웹으로 확장하면 위치 제공과 분석·피드백 저장 동의를 분리한다. 개인 이동 궤적 대신 코스 선택·삭제·평가처럼 필요한 최소 이벤트부터 검토한다.

### 편의성과 접근성

마우스로 누르기 쉬운 버튼, 키보드 이동, 지도와 같은 장소 목록, 명확한 출처 링크와 오류 안내를 유지한다. 고령자·유모차·휠체어 설정은 공식 접근성 자료와 실제 입구를 검수한 뒤 활성화한다. 오래된 무장애 자료만으로 현재 이용 가능을 확정하지 않는다.

> 운영 성능 목표는 최소사양에서 조건을 고정해 측정한다. 목표값은 다음 장의 계획이며 현재 측정 성과가 아니다. 외부 서비스 장애가 기본 탐색까지 중단시키지 않도록 기능별 상태를 분리한다. [E1, E6, L1]

### 검증 목표와 측정 방식

- 정확성  관광 후보 전수 검토율 100%, 확인된 중대한 오연결 0건. 유효 후보 수는 검수에 따라 줄어들 수 있다.
- 코스 제약  고정된 자동 시험 100건 이상에서 확인 가능한 시간·중복·배편·미지원 수단 제약 위반 0건.

- 사용성  도민·관광객 관점의 체험 과제로 출발지 이해·근거 확인·장소 교체·초기화 완료 여부를 기록한다.

> 위 수치는 제안하는 합격 기준이다. 추천 만족도와 실제 이동시간 오차의 측정 결과는 현재 없으며, 표본 수와 평가 조건을 함께 공개한다. [E1, L6]

## 14 검증 시나리오와 제출 산출물

시연은 현재 기능과 개선 기능을 구분하고, 정상 결과뿐 아니라 지원하지 않는 상황도 보여준다. 제출 직전에는 기획서의 완료 표기와 실제 코드·자료·모델 버전이 일치하는지 확인한다.

| 검증 상황 | 기대 동작 |
| --- | --- |
| 위치 허용·거절·획득 실패 | 출발 기준을 명시하고 실패 시 직접 선택. 공항을 내 위치로 대체하지 않음 |
| 좌표 없는 음식점·중복 지점 | 거리 코스 편입 제외 또는 재검수. 임의 좌표와 잘못된 지점 병합 금지 |
| 산 정상·섬·통제 관광지 | 입구와 수단 검수에 맞게 제외·대체하고 이유를 설명 |
| 시간 부족·귀환 불가 | 장소 수 축소 등 조정을 제안하고 성공한 일정처럼 표시하지 않음 |
| 자료 없음·API 중단·오래된 교통 | 거리 추정으로 동작하고 인기·실시간 표기를 해제 |
| 공용 PC 다음 사용자 | 새 여행 시작 후 저장·위치·조건·응답 잔존과 늦은 요청 복원 검사 |

### 제안 시연 순서

현재 구현 시연은 관광 검색 → 지도 묶음 전체 목록 → 공식 소개와 명부·지도 근거 → 음식 검색 → 상담 → 선택 장소 순서 초안으로 진행한다. 개선 기능이 완료되면 출발점 확인 → 자동 코스 대안 → 장소 교체 → 시간 재검사 → 오프라인 전환을 추가한다. 인기 방문 전이와 실시간 교통은 검증된 기능만 별도 시연한다.

### 제출 패키지

- 실행 코드와 모델  통합 흐름·검색·추천·전처리·학습·검증 코드, 모델 파일과 버전·입력·사용 범위
- 설치와 사용자 안내  내장 런타임·실행법·의존성·환경변수 예시·오류와 제약·공용 PC 초기화
- 데이터 활용 명세  허브·센터 필수 자료와 외부 자료의 출처·기준일·취득일·이용조건·가공·중복 처리
- 결과 설명자료  문제·Agent 구성·시연 결과·정확성·성능 검증·실패 사례·센터 활용과 확장 계획

> 공고의 기획서 필수 항목과 최종 ZIP 요구를 반영했다. 공개 본문에 없는 평가 배점이나 기획서 확장자는 임의로 가정하지 않는다. 실제 제출 전 갤러리의 입력 형식과 최종 공지를 다시 확인한다. [E1]
